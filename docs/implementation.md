# R01 実装仕様

対象は、同じGPU種別・メモリ容量のサーバー群と、同じモデル成分・期限・行動時間を持つロボット群です。S1は1成分、S2は0または1成分、義務モデルは複数指定できます。物理GPUの収容と仮定するworkerごとに1モデル成分を置きます。

## 入力

`problem.schema.json`で構造を検査し、revision、runtime fingerprint、GPU種別の一致、成分ID、周期指定、profileの順序を追加検査します。不明な設定キー、NaN、Infinity、重複JSONキーを拒否します。

`runtime_fingerprint`はdtype、入力画像・prompt分布、compile、CUDA Graphs、推論backendなど、プロファイルを失効させる条件をまとめた識別子です。GPU実測時にはresolved設定からハッシュを作り、任意の表示名を流用しないようにします。

プロファイルの`source`はsynthetic/measuredを分けます。measuredには根拠ログのSHA256と各測定点の件数・測定時間が必要です。この形式検査だけで測定内容の正しさを保証するものではありません。人工プロファイルの0Hz点は数理モデルの境界値であり、実測点として登録できません。

## 候補の生成

各モデル成分・バッチ設定・担当robot数kについて、集約到着率をS1はk*f、S2はk*f/H、義務モデルはk*periodic_hzとして問い合わせます。メモリとp99期限を満たす構成だけを整数計画へ渡します。profileのメモリ値は対象範囲の上限として与える必要があります。

測定点の間では平均遅延を線形補間し、p99は隣接点の大きい値を採用します。範囲外はunknownです。明示された`capacity_bound_hz`を超える場合だけ、その宣言モデル内でinfeasibleとします。容量上限を推測で設定しないでください。物理的な不可能性を証明する値ではありません。

## 整数計画と解の選択

OR-Tools 9.14.6206のCP-SATで、構成ごとの採用台数yを非負整数にします。

- 合計worker数は残りのGPU数以内。
- 必須の各モデルについて、合計担当robot数は全robot数と等しい。
- 義務モデルは台数最少、stream数で重み付けした平均遅延、安定したID係数の順。
- S1/S2はstream数で重み付けした平均遅延、台数、安定したID係数の順。

各目的を順に最適化し、その最適値を固定して次へ進みます。遅延のtie-breakだけ1マイクロ秒単位に切り上げます。SLOと閉ループ制約はこの丸め値を使いません。第三目的は構成ID順に付けた整数係数の和であり、完全な辞書式の一意性は保証しません。残る同率解は単一solver worker・seed 0・固定バージョンで選択します。

義務モデルで最少台数が未証明の場合は、余剰資源を勝手に確定しません。profile欠落が最少台数を減らす可能性がある場合もunknownです。

## 経路と閉ループ

構成ID順、robot ID順に割り当て、全成分を一度ずつ提供します。全robotについて`f*(t_act+mean_S1+mean_S2/H) <= 1`を検査します。独立したcheckerは、台数・被覆・経路・profile値・到着率・メモリも再計算します。

一つの配置がこの検査に落ちたことだけではinfeasibleを返しません。全候補の楽観的な最小遅延による上限、または次の必要条件でも不可能と証明できた場合だけinfeasibleとします。

```text
sum(y_p * streams_p * mean_latency_p / component_horizon)
  <= robots * (1/f - action_time)
```

この平均条件は全robotの条件より緩い必要条件です。整数化で左辺を切り下げ、右辺を切り上げているため、丸めで誤った不可能判定を強めません。この検算は論文の擬似コードに明記されていない本実装の補完です。必要条件を満たしただけではfeasibleにしません。

代替配置があり得るが未探索ならunknownを返します。`unresolved_packing.json`では、平均遅延の合計を最小化する1+3 stream配置が一部robotの閉ループ条件を外し、2+2配置なら成立します。このため全探索との違いを残しています。

`--recover-alternatives`はこの段階に追加する明示的な拡張です。GPU・構成を選ぶ0/1変数とrobotの割当変数を使い、構成ごとのstream数、成分の一意な被覆、GPU制約、robotごとの閉ループ制約を同じ整数計画へ入れます。遅延を切り上げ・時間予算を切り下げた保守的なモデルから得た正の解を、元の浮動小数のprofileで再検査します。量子化や時間切れによる解なしはunknownであり、全配置の不可能性の証明として使いません。

追加モデルの規模を8 robots・残余8GPUまでに制限します。論文の式(3)にrobot経路を含めるこの拡張は擬似コードに書かれたものではないため、出力に`algorithm_mode`と`recovery_used`を残して比較します。2Hzの反例では、paper_firstはunknown、拡張はfeasibleとなり、拡張の最大頻度も独立全探索の0.005Hz格子と0.01Hz以内で一致します。

## 周波数探索

0から1/t_actの範囲を二分探索します。平均・p99の測定値が到着率に対して非減少でないprofileでは、最適化を開始せずunknownを返します。個別周波数の検査は可能です。

未知の候補に当たったら、その点を不可能扱いして上限を削りません。既知の実行可能下限があれば返し、未解決の上限区間と理由を残します。0Hzは探索用の番兵であり、正の頻度の解が見つからなかったことだけで全頻度の不可能性を主張しません。0台のfleetは空配置・0Hzを返します。

既知解比較の格子は0.005Hz、productionの停止幅は0.01Hzです。基本5ケースと24の小規模S1構成はこの幅で比較します。独立oracleはproductionの補間・候補列挙・配置・経路を呼ばず、全ての既知候補のstream分割を列挙します。S1とS2の遅延を逆順に対応付けた最小最大ペア和を使い、productionのID順経路による限界も検出します。oracleは6 robots・8論理GPU以下に制限します。
