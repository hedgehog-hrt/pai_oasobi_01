# ローカル記録と永続保存

v0.20.15の確認1回目では、S1の待ち行列約2ms・モデル計算約95msに対して応答全体363msという要求があった。ホスト側の遅れを示すが、それだけで原因を断定はしない。Podの `/workspace` はネットワークFUSE、`/tmp` はローカルoverlayであることを確認した。計測中の圧縮観測・JSONLの同期書き込みが他の要求を遅らせる可能性を検証する。

v0.20.16は `staged_capture.create` で容量上限と空きを確認し、ローカルに専用の一時ディレクトリを作る。既存の実行器へ、その中の未作成の `output` を渡す。観測保存、記録内容、要求の送信・完了時刻、期限、頻度、モデル、Safetyと衝突判定は変更しない。計測時間の分母や遅い要求を除外する仕組みではない。

実行・監査後に `publish` が全ファイルを永続保存先へコピーする。コピー前後の原本と保存先を、パス・サイズ・SHA-256で照合する。成功した場合だけ `capture_transfer.json` を作る。途中失敗したコピーは完了と扱わず、ローカル原本も保持する。`remove_verified_source` は永続コピーを再照合してから、この実行が作った一時ディレクトリだけを削除する。コピー済み原本のシンボリックリンク、ハードリンク、容量超過、保存先の上書きは拒否する。

全試行で、保存先ファイルシステム・空き容量・転送時刻・全ファイルのハッシュ・一時領域削除を残す。モデル起動や推論中に失敗した実行も、残っている原本を先に永続保存してから不合格として処理する。Pod消失などで転送自体が不可能になった場合、ローカル記録は回収できない。この方式をネットワークへ逐次永続化した場合と同じ障害耐性とは扱わない。

## 次の固定比較条件

先行v0.20.15の確認3回は途中変更せず全て保存する。ローカル記録は別の探索300秒を行い、条件を満たした場合だけ新しい確認300秒×3回を行う。先行条件で失敗した反復を新条件の成功反復で置き換えない。

要求頻度・期限・p99定義・停止率90%以下・最低100判定・周期成立率99%以上を維持する。回復の継続と、3チャンク前の実タスク完了は、v0.20.15確認前に記録した補足と同じ定義を使う。新たな未回復を先行試験で置き換えない。

制御・モデル・物理のソースと設定が同一であることをハッシュで確認できる場合、先行v0.20.15の自然な回復検証を機能確認の参照として使用できる。許容する実行ソースの差分はバージョン表示と新しい保存機構だけ。停止率・期限・タスク成功率は参照試験から転記せず、各新試行の実測から計算する。保存先を移したCPU閉ループの元データを既存監査器で再検証し、コピー失敗・改変・領域外リンク・上限超過の検出も検証する。
